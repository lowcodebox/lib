## Как это работает

### 1. Альтернативы `lsof`

`lsof` — не единственный способ узнать, кто слушает порт. Более того, в минимальных Docker-образах его может не быть вовсе. Поэтому основными источниками данных выбраны нативные механизмы ОС, а `lsof` оставлен только как фолбэк.

| ОС | Основной способ | Что читаем / вызываем |
|----|-----------------|------------------------|
| Linux | `/proc/net/tcp` + `/proc/<pid>/fd` | inode сокета → PID, без внешних утилит |
| macOS | `netstat -anv -p tcp` | встроен в систему, есть всегда |
| Windows | `netstat -ano -p TCP` | встроен в систему |

#### Linux: `/proc/net/tcp` + `/proc/<pid>/fd`

Алгоритм:

1. Читаем `/proc/net/tcp` и `/proc/net/tcp6`. Каждая строка — открытый сокет. Нас интересуют только те, у которых поле `st == 0A` (состояние `LISTEN`), а локальный порт входит в диапазон `[from, to]`. Для каждой такой строки запоминаем пару `inode → port`.
2. Проходим по всем `/proc/<pid>/fd/*` и читаем симлинки. Слушающий сокет отображается как `socket:[<inode>]`.
3. Сопоставляем inode из шага 1 с PID из шага 2 — получаем список процессов, слушающих нужные порты.

Преимущества перед `lsof`:

- Нет зависимости от внешней утилиты.
- Работает в разы быстрее на системах с большим числом открытых файлов.
- Не требует парсинга человекочитаемого вывода.

#### macOS: `netstat -anv -p tcp`

На macOS `netstat` с флагом `-v` печатает PID процесса в последней колонке для слушающих сокетов. Пример строки:
```tcp4 0 0 *.8080 . LISTEN 12345```


Парсим строки с `LISTEN`, вытаскиваем порт из локального адреса и PID из последнего поля.

#### Windows: `netstat -ano -p TCP`

Аналогично — `netstat` с `-ano` печатает PID в последней колонке. Фильтруем строки `TCP ... LISTENING`.

#### Фолбэк на `lsof`

Если основной способ завершился ошибкой (например, `/proc` недоступен в контейнере, или `netstat` отсутствует), используется `lsof -nP -iTCP -sTCP:LISTEN`. Такой же фолбэк работает и на Linux, и на macOS, поскольку `lsof` есть в большинстве дистрибутивов.

### 2. Защита от TOCTOU-гонки

**Проблема.** Вы получили PID процесса X, который слушает порт. К моменту отправки сигнала X мог завершиться, а ОС могла отдать тот же PID новому процессу Y. Вы убьёте Y — не тот процесс, который хотели. Это классическая уязвимость *Time-of-Check to Time-of-Use*.

**Решение** реализовано в функции `stillSameListener`, которая вызывается непосредственно перед отправкой сигнала. Проверка состоит из трёх независимых условий:

1. **Процесс ещё жив.** На unix — `Signal(0)` (не отправляет сигнал, но проверяет существование и права). На Windows — `OpenProcess` с `PROCESS_QUERY_LIMITED_INFORMATION`.
2. **Время старта совпадает.** Для каждого найденного процесса сохраняется его start time:
    - **Linux** — поле `starttime` из `/proc/<pid>/stat` (тики с момента загрузки системы, переводим в секунды).
    - **macOS** — `ps -o lstart= -p <pid>`.
    - **Windows** — не используется (проверки 1 и 3 достаточны).

   Если время старта не совпадает — значит PID переиспользован, процесс пропускается.
3. **Процесс всё ещё слушает тот же порт.** Перечитываем список слушающих процессов в диапазоне и ищем совпадение по паре `(PID, port)`. Если процесс жив, но уже не слушает порт — его убивать незачем.

Между проверкой и отправкой сигнала остаётся микроскопическое окно, но для его эксплуатации ОС должна успеть переиспользовать PID именно в этот момент — на практике это исключено.

Если проверка не прошла, инкрементируется счётчик `Skipped` в отчёте — это не ошибка.

### 3. Graceful shutdown с таймаутом

Схема завершения каждого процесса:
TOCTOU-проверка
│
▼
SIGTERM ──────────────► процесс завершился? ──► да ──► Terminated
│ │
│ нет
│ │
│ ▼
│ ждём до timeout
│ │
│ ▼
└──────────────────► SIGKILL ──► Killed


Детали:

- **Таймаут передаётся параметром функции** `KillProcessesInPortRange(from, to, timeout)`. Это позволяет управлять балансом между скоростью и корректностью завершения.
- **`timeout <= 0`** — отправляется только `SIGTERM`, без ожидания и без последующего `SIGKILL`. Полезно для «мягкой» остановки, когда гарантии завершения не нужны.
- **Опрос живости процесса** — раз в 50 мс на unix, раз в 100 мс на Windows. Такой интервал даёт быструю реакцию без нагрузки на CPU.
- **`ESRCH` при `SIGTERM`** (процесс уже умер) — не ошибка, а `outcomeSkipped`. Процесс завершился сам, пока мы к нему шли.
- **Windows** не имеет `SIGTERM` в POSIX-смысле. Аналог мягкого завершения — `taskkill` без `/F`, принудительного — `taskkill /F` (соответствует `TerminateProcess`).
- **Отчёт** `KillReport` содержит раздельные счётчики `Terminated` и `Killed`, что позволяет понять, сколько процессов завершилось корректно, а сколько пришлось добивать.

## Ограничения

1. **Root / администратор.** Убить чужие процессы без соответствующих прав нельзя — ошибки `EPERM` попадут в `KillReport.Errors`.
2. **`/proc` в контейнерах.** В некоторых контейнерах `/proc/net/tcp` показывает сокеты хоста, а не namespace. Если это ваш случай — используйте фолбэк на `lsof` или запускайте с `--pid=host`.
3. **Точность `starttime` на Linux.** Значение читается в тиках (`HZ=100` по умолчанию), т.е. точность 10 мс. Два разных процесса с одинаковым PID (переиспользованным) и одинаковым временем старта в пределах 10 мс — теоретически возможны, практически нет.
4. **macOS `ps -o lstart=`** возвращает локальное время без таймзоны. `time.Parse` использует UTC. Для сравнения «равно / не равно» это неважно — обе стороны парсятся одинаково.
5. **Гонка при чтении `/proc/<pid>/fd`.** Процесс может умереть между `ReadDir` и `Readlink` — это безопасно, ошибка просто пропускается.
6. **Только TCP LISTEN.** UDP-порты не покрыты. Если нужно — добавьте `/proc/net/udp` (Linux) и `netstat -anu` (macOS / Windows).
7. **Межплатформенная сигнатура.** На Windows `SIGTERM` не существует; `taskkill` без `/F` не всегда даёт процессу шанс корректно завершиться. Если нужен настоящий graceful shutdown на Windows — потребуется отдельный механизм (например, именованные события или `WM_CLOSE` для GUI-приложений).
